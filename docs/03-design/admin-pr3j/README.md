## 1. Lifecycle and readiness

- `trainers.is_active` (operational) is separate from `scheduling_readiness` (`needs_setup` | `ready`), with `readiness_origin` (`grandfathered` | `admin_confirmed`), `readiness_confirmed_at/by` (genuine Admin confirmation only) and `readiness_version`. List states are mutually exclusive: **Ready** (active + ready), **Needs setup** (active + needs_setup), **Inactive**.
- New trainers always start `needs_setup`. Reactivation returns to `needs_setup`.
- Trainer Picker requires all four: active, ready, linked to the course, not excluded — enforced server-side, not by UI visibility.
- **Confirm ready for scheduling** is a separate action, never combined with a save. Enabled only when: (1) active, (2) ≥ 1 *effective* eligible course (linked and not excluded), (3) module exclusions acknowledged for the current eligibility version, (4) no unsaved eligibility changes. It opens a confirmation dialog (effective course count, SME count, exclusions, trainer version) and writes `scheduling_readiness_changed` with actor, time, trainer version and eligibility version.
- **Versioning of eligibility:** every eligibility save increments `trainers.version` and `eligibility_version`. For an additive change (link added, exclusion removed, SME toggled) a valid exclusion acknowledgement is carried forward to the new eligibility version and the original readiness confirmation actor/time/version are left unchanged. A reset-trigger change (link removed, exclusion added) or deactivation clears the acknowledgement and returns the trainer to `needs_setup`.
- **Reset rule [Owen, 2026-09-04, reaffirmed 2026-09-06]:** readiness returns to `needs_setup` automatically on (a) deactivation, (b) removal of any eligible course link, (c) adding an exclusion. Adding a link, removing an exclusion or toggling SME does **not** reset readiness. The exclusion acknowledgement (condition 3) is invalidated by exactly the same events, never by additive changes. Applied server-side inside the eligibility save transaction regardless of future assigned sessions; recorded in the same `course_access_changed` event (`metadata.readinessReset = true`); existing session assignments are never touched. PR3K (per `docs/01-product/trainer-rate-reconciliation.md`) may create a trainer identity in `needs_setup` but creates no course links or exclusions; eligibility and readiness are completed only through this PR3J workflow, so no import-origin clause is needed.
- Grandfathering (exact, unchanged from V5): existing trainers become `ready` with `readiness_origin = grandfathered` iff `is_active AND EXISTS (trainer_courses row whose course_code is NOT in module_excludes)`; all others `needs_setup`. Migration test compares the complete `(course_code, trainer_id)` picker result set before and after.

## 2. Eligibility model

- **Links and exclusions are independent records [Owen, accepted from Sol].** A course may be linked (`trainer_courses`) and excluded (`module_excludes`) at once; the exclusion wins; the row is labelled "Excluded — unavailable for scheduling". Adding an exclusion never deletes a link or SME flag; removing an exclusion restores the link's effect without recreating it. Duplicate links or exclusions are impossible (server-validated). Seeds contain no overlap today; the model exists for imports.
- SME (`trainer_courses.is_sme`) can be set only on an existing link; removing a link removes its SME flag in the same pending change. SME is described only as "Subject matter expert"; no score, boost, rank or recommendation effect is shown (PR4 scope).
- Eligible courses are shown grouped by programme (`programmes.name`, tones FTDM blue / FTIIO amber / DGAI purple / ASK standalone grey), each row: code pill, exact canonical title (ellipsis + `title` on desktop, wrapped on mobile), SME checkbox "Subject matter expert for [code]", "Remove [code] eligibility". **Add eligible course** and **Add exclusion** are searchable combobox/listbox controls over active canonical courses (search by code or exact title; already-linked courses marked "Added"; no free-text creation).
- Acknowledgement: "I have reviewed module exclusions; none are missing" — required for confirmation, tied to the eligibility version, enabled only when there are no unsaved changes.
- **Save eligibility changes** is one atomic, version-checked write covering links, SME and exclusions; it never confirms readiness. For a Ready trainer, an inline warning appears before saving only when the pending change contains a reset trigger (link removal or exclusion added): "Saving these changes will move this trainer to Needs setup. Confirm readiness again after reviewing the saved record."

## 3. Aliases [Owen: display + search + Add alias]

- Scope **[Owen, 2026-09-06 and 2026-09-07]**: display, search, **Add alias** and audited **Remove alias**.
- **Remove alias (contract):** each existing alias chip carries a remove control with accessible name `Remove [alias] alias` (visible × icon, `title` "Remove alias"; keyboard: Tab reaches each chip's control, Enter/Space opens the confirmation. Focus: Cancel, Escape, or a failed/stale removal restores focus to the original alias-removal control; only after a successful removal — when that control no longer exists — does focus move to the next chip's control, or to **Add alias** when the removed chip was last). The confirmation dialog (≤ 520 px, `role="dialog"`, focus trapped, Escape cancels) shows the exact alias and its source label, the trainer name, ID and current version, the warning "Future imports may no longer match this alias." with the consequence (rows using that alias fall to manual resolution until mapped again), and a **required** audit note (1–500 characters, live count; Remove disabled until non-empty). Secondary Cancel, filled-danger **Remove alias**. No optimistic UI.
- Server: `DELETE /admin/trainers/:id/aliases/:aliasId` (or equivalent) requires the trainer's current `expectedVersion` and the note; in one transaction it removes the current alias mapping, increments `trainers.version`, and appends exactly one immutable `alias_removed` event whose `metadata` retains `{ aliasName, source, note }`; stale `expectedVersion` returns the typed 409 and nothing is written. The primary trainer name is not an alias and has no remove control; the route rejects any attempt to remove it. Earlier history is never modified. Success updates the drawer chips, the list/search results (the removed alias no longer matches) and the History tab together with a `role="status"` message "Alias "[alias]" removed." No rate data is read or written; PR3K reconciliation is untouched.
- `trainer_aliases.alias_name` with source labels: `tms` and `schedule_excel` → "Master schedule", `rate_excel` → "Rate workbook", Admin-entered → "Admin entry". Shown as chips in the Overview tab and as a muted line under the name in the list; searchable.
- Aliases are trimmed and case-normalised; unique index on `lower(btrim(alias_name))`; typed 409 on duplicate; migration preflight detects existing normalised duplicates and STOPS. Registration creates no alias automatically.

## 4. Identity and versioning

- `trainer_id` is generated by the server on registration, immutable, shown as muted metadata (never an editable field) **[Owen, accepted from Sol]**. Names are compared case-insensitively after whitespace normalisation; a possible duplicate blocks registration with an inline error; no silent merge.
- Creation returns `version = 1`; every subsequent write requires `expectedVersion`, increments `version`, and writes exactly one event in the same transaction; stale writes return a typed 409 and the UI disables writes, shows "This trainer changed after you opened it. Reload the latest version before saving." with **Reload trainer**, confirming before discarding unsaved input.

## 5. Change history

Append-only `trainer_change_events` on the `user_access_events` pattern (typed action enum, `actor_user_id` NOT NULL, before/after `is_active`, `scheduling_readiness`, `version`, `note` ≤ 500, JSONB `metadata`, append-only trigger). Actions: `trainer_created`, `trainer_updated`, `trainer_deactivated`, `trainer_reactivated`, `alias_added`, `alias_removed`, `course_access_changed`, `scheduling_readiness_changed`. One eligibility save produces one `course_access_changed` event whose `metadata` holds the structured diff (links added/removed, SME on/off, exclusions added/removed) and any automatic reset; the History tab renders that diff as human-readable lines within the single event ("Added FTDM-SMM · SME enabled on FTDM-DME"; "Added exclusion DGAI-HR · Readiness reset: Ready → Needs setup"). A save that triggers a reset never produces a second event; the reset is part of the same `course_access_changed` entry. `alias_added` / `alias_removed` render as "Alias added" / "Alias removed" with the alias in quotes, its source label, the note and the resulting version. Newest first; actor display name or email, never a raw id unless nothing else exists; `D MMM YYYY, h:mm am/pm` Singapore; resulting version. No edit, delete or undo.

## 6. Deactivation and reactivation

- The API returns the exact **affected upcoming session count**: sessions assigned to the trainer, not cancelled or completed, `end_date` ≥ today (Asia/Singapore); used in the list column and the dialog. If it cannot load, Deactivate is blocked with "Upcoming-session impact could not be checked. Retry before deactivating." and other edits stay usable.
- Deactivate dialog (≤ 520 px): "[N] current or upcoming sessions will remain assigned to this trainer." (0 → "This trainer has no current or upcoming session assignments."; 1 → singular), always "Deactivation prevents new assignments. It does not unassign existing sessions or remove history. Reactivation returns the trainer to Needs setup."; optional audit note (≤ 500, becomes the event note); required checkbox "I understand existing session assignments will remain unchanged"; secondary Cancel, filled-danger Deactivate trainer. No optimistic UI.
- Reactivate: smaller confirmation, copy "Reactivation returns this trainer to Needs setup. Review eligibility and confirm readiness before scheduling."

## 8. States

Initial list loading (header/tabs kept, 5 row / 3 card skeletons, `aria-busy`, no false zero counts) · Refresh (rows kept, "Refreshing trainers…") · List error ("Trainer records could not be loaded." + Retry; no stale counts shown as current) · Tab empty ("No trainers are ready for scheduling." / "No trainers need eligibility setup." / "No inactive trainers.") · Search empty ("No trainers match "[query]" in [state]." + Clear search) · No links ("No eligible courses added. Add at least one course before confirming readiness.") · No exclusions ("No module exclusions recorded." — acknowledgement still required) · Course search empty ("No canonical courses match "[query]".") · Drawer loading (opens immediately with skeletons, Close available) · Drawer error (kept open, "Trainer details could not be loaded" + Retry) · Mutation error (input kept, field errors attached, alert summary, controls re-enabled) · Success (`role="status"`, row + counts + drawer + history updated together) · 401 (global handling) · 403 ("Admin access is required for Trainer Directory.", no partial data) · 404 after selection (drawer closes, "This trainer is no longer available", list refreshes) · Stale 409 (§4) · Impact-count error (§6).
